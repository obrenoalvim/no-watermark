## Pending Changes

### Preserve legitimate bidi marks/isolates and paired embeddings by default (highest-impact item below)
- **Category:** Feature (default-behavior change)
- **Source:** Reference test suite at [guillaumemeyer/watermarks-remover `tests/test_clean_text.py`](https://github.com/guillaumemeyer/watermarks-remover/blob/main/tests/test_clean_text.py) — see `test_preserves_legitimate_bidi_marks_and_isolates_by_default`, `test_preserves_legacy_bidi_embeddings_by_default`, `test_strips_orphaned_bidi_embedding_controls`
- **What:** Right now `nowatermark` strips every bidi control codepoint unconditionally (they all fall through to the generic Cf `"format-char"` bucket). The reference tool instead preserves, by default: LRM/RLM (U+200E/200F) and the directional isolates LRI/RLI/FSI/PDI (U+2066–2069) always; and *paired* LRE/RLE...PDF embeddings (U+202A/202B opened, correctly closed by a matching U+202C) as a matched pair. It still strips, always: RLO/LRO overrides (U+202D/202E, these actively reorder text and are the real attack vector) and any *orphaned* embedding/override control that has no matching pair. A `strip_bidi=True` escape hatch removes everything unconditionally, matching this tool's current blanket behavior.
- **Where:** `src/nowatermark/detector.py` (the bidi subset of Cf needs its own category instead of falling into generic `format-char`) and `src/nowatermark/remover.py` (a paired-embedding scanner, structurally identical to the existing `_valid_flag_tag_indices` — same "find matched open/close spans" shape, just for U+202A/202B → U+202C instead of flag-base → cancel-tag).
- **Why:** LRM, RLM, and directional isolates are exactly what correct rendering of mixed-direction text needs — e.g. an Arabic sentence with an embedded English word, number, or the reference example `السعر ⁦123 USD⁩‏` (price, then an isolated LTR run for the number+currency, then RLM). Stripping them unconditionally doesn't just remove a watermark carrier, it can visually scramble legitimate Arabic/Hebrew/Persian/Urdu prose the same way un-guarded ZWJ stripping would scramble emoji. This is the exact same risk class the emoji-adjacency guard already exists to prevent, just for RTL scripts instead of emoji — and it affects a much larger population of real users than the Hangul/Khmer/Mongolian item below.
- **Risk:** This changes default output for any text containing legitimate bidi marks (a real behavior change to already-shipped `clean()`, not purely additive) — existing users/scripts relying on current blanket-strip behavior would see different output after upgrading, so it needs a changelog note or a major-version bump, not a silent patch. Implementation risk is well-understood since the paired-embedding-scanner pattern is proven in this codebase already (mirrors the flag-tag-sequence fix from this same cycle) — the main work is getting the "orphaned vs. paired" distinction right, which the reference's own tests spell out precisely (see Source links above for exact input/output pairs to replicate as tests).
- **Effort:** Medium (the scanning logic is a known pattern to copy; the design/testing effort is in matching the reference's exact orphan-vs-paired semantics and deciding whether to default-match it or ship behind a flag first)
- **Related, smaller finding from the same comparison:** the reference also preserves the *first* variation selector immediately following a CJK ideograph (Unicode Han standardized variation sequences select a specific glyph form) but strips a second one stacked on the same base as contraband. `nowatermark` currently strips all variation selectors unconditionally. Same complexity class as this item (context-dependent single-selector preservation) — worth doing in the same pass if this item gets picked up.

### Trailing-whitespace stripping (SNOW steganography)
- **Category:** Feature
- **Source:** https://darkside.com.au/snow/ (SNOW tool), https://arxiv.org/html/2502.12710 (Innamark, IEEE Access 2025)
- **What:** Strip trailing spaces/tabs at the end of each line. SNOW is a decades-old, well-documented steganography technique that hides a payload in trailing whitespace, which is invisible in virtually all text renderers.
- **Where:** New function in `src/nowatermark/remover.py` (e.g. `_strip_trailing_whitespace`), called from `clean()`; new `detector.py` category `"trailing-whitespace"`.
- **Why:** Currently completely undetected — `nowatermark` only classifies individual codepoints, and this technique uses ordinary space/tab characters at an unusual *position* (line end), not a special codepoint. Real gap in the tool's stated goal of "detect and remove invisible-Unicode watermarking."
- **Risk:** Markdown uses exactly two trailing spaces at end of line as a hard line-break convention (widely used). Blanket stripping would silently break that formatting for any Markdown source passed through `clean()`. Needs either an opt-in flag (default off) or a Markdown-aware exception (skip stripping when exactly 2 trailing spaces). Product call: is breaking that convention acceptable for a tool whose whole point is "strip anything invisible," or does it need the exception?
- **Effort:** Low (the strip itself is a few lines; the design decision is what takes judgment)

### Homoglyph / lookalike-character normalization (removal, not detection)
- **Category:** Feature
- **Source:** https://bunnylab.github.io/unicode-steganography (`pyUnicodeSteganography`, "lookalike" method); confirmed as a currently-shipping technique in independent researcher Pasquale Pillitteri's text analyzer (https://pasqualepillitteri.it/en/news/10551/claude-invisible-watermark-text-c2pa, Aug 2026) and covered by BleepingComputer's survey of the August 2026 AI-watermark-remover tooling wave (https://www.bleepingcomputer.com/news/security/ai-watermark-removers-flood-the-web-almost-none-can-prove-they-work/)
- **What:** *Detection* of this (mixed-script word flagging) already shipped this cycle — see `src/nowatermark/homoglyphs.py` and `nowatermark detect`'s "possible homoglyph substitution" section. What's still open is *normalization*: automatically rewriting flagged homoglyphs back to Latin as part of `clean()`.
- **Where:** Extend `src/nowatermark/homoglyphs.py` with a confusables table (Unicode publishes an official `confusables.txt`) and a `normalize()` function; new CLI flag, e.g. `nowatermark clean --normalize-homoglyphs`.
- **Why:** Detection alone tells the user something is suspicious but doesn't fix it. Now validated as real-world-relevant, not speculative — an outside researcher's tool flags this exact class as of this week.
- **Risk:** Same as before — this changes *visible* characters, not invisible ones. It's lossy for legitimate non-Latin-script text (Russian, Greek, Serbian names/words mixed into otherwise-English prose). Detection's per-word mixed-script heuristic has a low false-positive rate (mixing scripts *within one word* is genuinely rare in legitimate text), but auto-rewriting on that signal is a bigger commitment than just flagging it — must ship opt-in only, off by default.
- **Effort:** Medium (confusables table is available pre-built from Unicode; the false-positive-avoidance heuristic is now half-done since detection already exists)

### Script-aware preservation of Hangul/Khmer/Mongolian invisible glue marks
- **Category:** Feature
- **Source:** Direct code comparison against [guillaumemeyer/watermarks-remover](https://github.com/guillaumemeyer/watermarks-remover) (`service/scripts/text_unicode.py`), the leading open-source tool in this space (13k+ stars)
- **What:** Three invisible-mark families are load-bearing in their own scripts and should only be preserved when they immediately follow a matching-script base letter, stripped otherwise: Mongolian Free Variation Selectors (U+180B–180D plus U+180F FVS4 — a fourth selector added to Unicode after the reference tool's list was written, found via a second independent tool, `mikiane/claude-watermark-cleaner`; same context-dependent rule applies), Khmer inherent vowels (U+17B4–17B5, invisible but phonemic after a Khmer consonant), and Hangul choseong/jungseong fillers (U+115F–1160, hold a jamo slot in a partial syllable block). Currently `nowatermark` does not classify any of these at all — they pass through untouched regardless of context. (Note: U+3164 HANGUL FILLER, a *different* character in the Hangul Compatibility Jamo block with no script-glue role, was resolved separately this cycle — added unconditionally to `OTHER_INVISIBLE`, not part of this context-dependent item.)
- **Where:** `src/nowatermark/detector.py` (new categories) and `src/nowatermark/remover.py` (script-context check, same shape as the existing ZWJ/ZWNJ emoji-adjacency guard: look at the preceding kept character's script, not just its identity).
- **Why:** Currently a real, if narrow, completeness gap — an isolated (non-script-adjacent) instance of one of these is exactly the kind of "technically invisible, currently unclassified" character the tool's whole premise is to catch, and the reference implementation treats them as first-class categories.
- **Risk:** Low likelihood of affecting this tool's actual userbase (requires Mongolian/Khmer/Hangul text specifically), but implementing the script-adjacency check correctly needs care to avoid breaking legitimate Korean/Khmer/Mongolian prose passed through `clean()` — same class of risk the existing emoji-guard already manages successfully, so the pattern is proven, just needs applying three more times with the right script-range tables.
- **Effort:** Medium (three narrow script-range tables plus adjacency logic mirroring the existing emoji-guard shape; the tricky part is comprehensive test coverage in scripts the maintainer may not read)
